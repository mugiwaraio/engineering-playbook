# Git 合并与冲突处理策略

## 安全原则

- 合并、变基、同步分支或处理冲突前，先检查 `git status`、当前分支、相关提交历史和差异；同步前先获取最新远程引用。
- 工作区已有修改是用户资产：不得覆盖；与任务无关的文件尽量不动；若会影响 Merge，先说明风险。
- 需用户明确授权才可执行：`git reset --hard`、`git clean -fd`、`git checkout -- .`、`git restore .` 等批量丢弃本地修改的命令，改写已发布历史，以及任何形式的强制推送。
- 任何情况下不做：静默删除任一分支的有效功能、删除不理解的代码、大规模无关格式化、顺便重构无关代码。
- 不主动 push。用户要求提交时创建正常 Merge Commit；要求 push 时执行普通 `git push`；必须改写远程历史时先说明风险，并用 `git push --force-with-lease`，不用 `--force`。

## PR 分支同步

已发布并对应 PR 的分支，默认将目标分支 merge 进 feature 分支，不 rebase、不重写已发布历史；除非仓库规范或用户明确要求，且改写前先说明影响。

## 冲突处理

- 按语义解决冲突：先理解 merge base 和两个分支各自的修改意图，再定最终结果；不得机械选择 ours/theirs/both，不得仅凭 `<<<<<<<`、`=======`、`>>>>>>>` 三段文本猜测。
- 保留双方有效且互不冲突的修改：目标分支较新的修复与改进、feature 分支要实现的功能；删除合并产生的重复代码、配置、测试和文档。
- 非简单冲突按需检查 merge base、双方分支版本、提交历史、调用方、测试、文档和注释：

  ```bash
  git merge-base / git log / git diff / git show / git blame
  git show :1:<path>   # merge base
  git show :2:<path>   # 当前分支
  git show :3:<path>   # incoming 分支
  ```

- 检查后仍无法确定正确语义时停止处理，不得猜测、不得为让状态干净随意选边；报告冲突文件位置、双方意图和不同解法的影响，可给推荐方案但不得隐藏不确定性。

## 特殊文件

- 自动生成文件：先解决源文件，再用仓库已有命令重新生成。
- 依赖：先解决 Manifest（`package.json`、`go.mod` 等），再用对应包管理器重新生成 Lockfile，保持二者一致；不手工拼接 Lockfile；不删除真实需要的依赖，不顺便升级无关依赖。
- 数据库 Migration：视为高风险。不得重写、删除、重编号已可能在其他环境执行过的 Migration；不假设生产数据可重建，考虑向前兼容与回滚；双方各自新增 Migration 时保留双方，按项目机制解决顺序。
- 文档：保留双方独有信息，删除重复内容，保持逻辑清晰。

## 测试与 CI 门禁

- 不得为让 Merge 成功或 CI 通过而：删除测试（含 Regression Test）、降低断言强度、降低 Coverage 或 Mutation 阈值、禁用 Lint / Type Check / Build / Race 检查 / E2E / 安全扫描，或用 `|| true`、忽略 exit code、skip、注释检查等方式绕过失败。
- 业务行为合法变化时更新测试期望，而不是删除测试。
- 冲突解决后测试或 CI 失败：先判断是否由本次 Merge 引入，修复真正的逻辑、兼容性或集成问题；与本次 Merge 无关的失败明确说明。

## 安全相关冲突

- 认证、授权、凭据、加密、输入校验、安全扫描、Secrets、IAM 等安全相关内容的冲突，默认保留更严格且符合现有设计的版本。
- 不得因 Merge 冲突降低安全级别，不得将 Fail-Closed 改为 Fail-Open（安全底线，任何情况不可违反）。
- 双方安全策略存在实质冲突时，先确认设计意图，不得默认选择更宽松版本。

## 完成标准

全部满足才算完成，未满足或无法执行的项必须明确报告：

1. 无 Unmerged Paths，真实冲突标记已清除（可用 `git grep -nE '^(<<<<<<<|=======|>>>>>>>)'` 搜索；正常文件合法包含类似文本时做语义确认，不能仅凭搜索结果判断）。
2. `git diff --check` 通过，最终 Diff 已检查（`git diff`、`git diff --cached`）。
3. 双方有效修改无误删，无重复实现或重复文档。
4. 未降低安全、测试或 CI 门禁。
5. 已执行修改范围要求的测试和验证。

## 完成报告

- 冲突文件、重要冲突的语义原因及解决方式。
- 双方内容的取舍：保留了什么，删除了哪些重复或被替代的内容。
- 实际执行的验证命令及结果。
- 剩余的不确定性和需用户确认的风险；若无剩余语义冲突，明确声明。
