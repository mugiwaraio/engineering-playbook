# AI 编码规范

> 本规范完整适用于服务端应用项目。脚本、CLI 工具、前端等项目遵守第 11 章优先级体系：第一层和第二层始终适用，第三层按项目规模判断。

### 1 开发模式

- 先写测试，再写最小实现使测试通过，最后重构。
- 探索性开发可先写试验代码验证可行性，接口稳定后补测试驱动重写。试验代码不可直接进入主分支。

### 2 设计原则

- 模块职责单一且清晰，优先保证可读性、可测试性和可维护性。
- 避免过度抽象：一层能解决的不拆两层。不为只用一次的操作创建工具函数；不为假设的未来需求预留扩展点；不为不可能发生的场景添加错误处理和降级逻辑。三行相似代码优于一个过早的抽象。
- 拆分判断：无法用一句话描述"做什么"则应该拆；拆分后调用方需了解内部细节才能正确使用则不该拆。
- 代码结构：
  - 函数只做一件事，命名能说清职责。超过 40 行的函数审视是否应拆分。
  - 模块通过公开接口交互，隐藏内部实现。调用方不需要了解内部逻辑即可正确使用。
  - 按业务职责拆分而非按技术层。一个完整的业务概念（如定价计算、权限校验）内聚在一个模块中。
  - 新增行为优先通过扩展（新增模块、新增实现）而非修改已有代码。核心模块定义接口，具体实现可替换。裁决判据：第二个实现真实出现时才引入接口，只有一个实现时不预先抽象（与本章"不为假设的未来需求预留扩展点"配套）。
  - 依赖单向流动，禁止循环依赖。高层模块定义接口，低层模块实现接口。
- 先分析问题本质、目标、约束和失败模式，再给设计方案。选了常见方案要能说明为什么它适合当前场景。
- 不臆造需求、接口、依赖、数据或环境。不引入技术栈以外的依赖，需要时先确认。信息不足时明确假设，基于最小假设给可执行方案。
- 新功能的默认值选最安全、最保守的选项，用户显式 opt-in 才放宽限制。宁可要求显式配置，不提供危险的便捷默认值。
- 命名约定：实体类大驼峰，不加前缀后缀（如 Provider、Agent、ChatMessage）；字段小驼峰（如 apiKey、baseUrl、modelName）。

### 3 单元测试

- 覆盖正常路径、边界条件、异常路径和关键失败场景。
- CI 全量测试必须 100% 通过，任何失败阻断合并。禁止以 skip、注释用例、删除测试、放宽断言等方式换取通过；Flaky 测试按第 9.1 节处理。
- 开发项目（非 spike/试验分支）：新增/变更代码（PR diff）必须达到 **100% 行覆盖 + 100% 分支覆盖**。全仓覆盖率实行 ratchet：以引入门禁时的实测值为基线，只升不降，目标 ≥ 80%；已达 80% 的仓库不得跌破 80%。均由 CI 强制，未达标不得合并。AI 生成代码属"新增代码"，必须全覆盖，防止局部小缺陷演化为大漏洞。存量代码缺口体现在基线中，不阻塞合并，但禁止在其上新增未覆盖逻辑。
- 覆盖率只证明代码被执行，不证明断言有效。核心业务模块必须引入变异测试（mutation testing，如 Stryker/PITest），变异得分（击杀率）≥ 70%，各项目可在覆盖率配置中注明理由后调整该阈值，但下调不得低于 60%，杜绝"无断言/弱断言"的空壳测试。
- 仅允许排除纯样板代码（自动生成代码、DTO、纯转发包装）；每条排除项须在覆盖率配置中注释理由，禁止用排除规避业务逻辑测试。
- 只 mock 你不拥有的东西（外部 API、第三方服务）。项目内部模块优先用真实实现。
- 数据库等基础设施在单元测试中可用内存替代（SQLite、testcontainers），集成测试中必须用真实实现。
- 不确定性依赖（时间、随机数）通过接口注入控制，不直接 mock 标准库。

### 4 文档同步

- 若改动影响使用方式、接口、配置项、运行步骤、目录结构或测试方式，必须同步更新相关文档。
- 文档同步是实现计划的必要步骤，不是事后补充。制定计划时必须将文档更新作为独立 Task 列入。
- 需检查的文档范围：README、CLAUDE.md、API 文档（OpenAPI/Protobuf）、配置说明、部署文档、CHANGELOG。
- 判断标准：如果一个新加入项目的开发者只看文档（不看 diff），能否正确理解当前系统行为？如果不能，文档需要更新。

#### 4.1 需求记录

- 每次收到新需求，先将需求写入项目 `docs/requirements.md`（需求文档），再开始实现；目录或文件不存在时先创建。适用于功能开发项目；纯文档/规范仓库、一次性脚本可豁免，豁免决定在首个相关 commit message 中注明。
- 条目按时间顺序追加到文件末尾，只追加不修改历史条目；需求变更、追加、废弃均作为新条目记录，保证历史可追溯。
- 条目格式（需求日期精确到分钟，需求详情逐条编号，保留用户原始意图，不混入实现细节）：

  ```text
  需求日期: 2026-07-28 21:07
  需求详情:
  1. aws costs 菜单中新增一列显示用户邮箱，放在用户账号 ID 左侧。
  2. 该功能做成通用组件，供后期全局使用。
  ```

- 实现该需求的 commit message 中引用需求日期（如 `feat: aws costs 列表新增用户邮箱列（需求 2026-07-28 21:07）`），实现与需求可双向追溯。

### 5 配置管理

- 环境相关的可变配置统一通过配置文件或环境变量管理，禁止硬编码在业务代码中。
- 配置项集中定义，有清晰命名、默认值和说明。
- 密钥禁止放入配置文件或代码仓库。

### 6 错误处理与日志

- 错误要么处理，要么向上传播并附加上下文。禁止静默吞掉，禁止 catch 后仅打日志然后继续执行。违反：`catch (e) { log(e); }` 然后继续执行。合格：`catch (e) { throw new ServiceError('订单创建失败', { cause: e }); }`。
- 日志包含 who（请求 ID）、what（操作）、why（原因）。禁止无信息日志。违反：`logger.error("failed")`。合格：`logger.error(\`用户 ${userId} 创建订单失败: ${err.message}\`)`。
- 禁止在日志中记录密码、密钥、Token 等敏感信息。

### 7 安全编码

- 所有外部输入视为不可信。SQL 用参数化查询，命令行用参数数组，HTML 输出做上下文编码。
- 校验顺序：先规范化输入（路径 resolve、大小写统一、编码解码），再做安全校验，最后执行操作。顺序颠倒会导致校验被绕过。
- 认证失败 fail-closed（默认拒绝）。授权检查在服务端执行。
- 密码存储用 bcrypt/scrypt/argon2。密钥/Token 必须有过期机制。
- 状态变更请求须防范 CSRF（Token 校验或 SameSite Cookie）。
- CORS 使用白名单模式，禁止 `Access-Control-Allow-Origin: *`（本地开发环境除外）。
- 依赖供应链：锁文件（lockfile）必须提交入库，生产依赖钉死版本，禁止 `latest`/宽松范围放任漂移。
- 引入新依赖前评估维护活跃度、许可证、已知漏洞；只从官方可信源安装，警惕仿冒包名（typosquatting）。不引入技术栈外依赖（见第 2 章）。
- CI 集成依赖漏洞扫描（SCA，如 npm audit / Dependabot / Trivy），高危漏洞阻断合并。

#### 7.1 安全审计

- 进行代码安全审计、bug 查找、漏洞挖掘时，应使用当前可用的最强模型 + 最高推理档位，不为省时间降档。模型与档位由用户在客户端选择，AI 发现当前配置低于该要求时应主动提醒用户切换。具体型号清单维护在 `docs/vibe-coding-cli-toolchain.md`，不在本规范中钉死。
- 审计必须逐类覆盖以下检查项，每类标注"通过 / 不适用 / 发现问题"：
  - 注入类：SQL 注入、命令注入、代码注入、XXE。
  - 前端与会话：XSS、CSRF。
  - 服务端请求与文件：SSRF、任意文件读取、文件包含（RFI/LFI）、文件上传。
  - 认证与授权：权限越权（水平/垂直）、弱口令。
  - 信息与配置：敏感信息泄漏、运维配置不当。
  - 其他：业务逻辑缺陷、框架或组件通用型漏洞（对照已知 CVE）。

### 8 服务端编码

> 本章适用于长驻服务端进程。CLI 工具、脚本、前端项目按实际需求选用适用的小节。

#### 8.1 可观测性

- 结构化日志 + 关键接口的延迟和错误率指标。
- 多服务调用链时接入分布式链路追踪，透传 trace_id / request_id。trace_id 注入在框架中间件层统一实现，禁止依赖手动传递。

#### 8.2 可靠性

- 所有外部调用必须设置超时，禁止无限等待。
- 重试必须有上限（通常 3 次）、指数退避 + 随机抖动，且区分可重试错误（超时、503）和不可重试错误（400、404）。
- 涉及支付、订单等写操作的接口必须支持幂等。通过 idempotency key、数据库唯一约束或状态机保证。幂等 key 需定义 TTL（不短于业务最大重试窗口）。
- 每个服务暴露健康检查端点。K8s 环境区分 Liveness 和 Readiness 探针。
- 优雅停机：收到终止信号后停止接收新请求，等待处理中的请求完成（设最大超时），关闭连接池和后台任务后退出。
- 下游依赖持续失败时应快速失败（熔断），而非排队等超时。安全相关依赖不适用降级（见第 7 章）。
- 对外暴露的 API 应实施速率限制。

#### 8.3 数据库

- 事务边界在 Service 层管理，Repository 层不自行开启事务。事务范围尽可能小，禁止在事务中做远程调用或耗时操作。
- Schema 变更必须使用版本化 migration 工具管理，禁止手动执行 DDL。每次变更有对应的回滚脚本。
- 禁止无 WHERE 条件的 UPDATE/DELETE。查询关注执行计划，避免全表扫描和 N+1 查询。
- 大表 DDL（百万行以上）：评估锁影响，必要时使用 online DDL 工具。
- MySQL 详细规范（表设计、SQL 编写、事务与连接、账号权限、Migration）见 `rules/databases/mysql.md`。

#### 8.4 并发与资源

- 共享可变状态必须有显式同步机制（锁、原子操作、channel 等），并在注释中说明保护策略。
- 外部资源（数据库连接、HTTP client、文件句柄）通过池化管理，禁止每次请求新建连接。
- 后台任务必须有生命周期管理：可取消、有超时、有错误上报。禁止 fire-and-forget。
- 资源使用有上限约束（连接池大小、队列长度、并发数），防止无限增长。

#### 8.5 API 设计

- 接口变更必须向后兼容：新增字段可选，不删除已有字段，不修改已有字段语义。破坏性变更通过版本号区分。
- 路径格式：`/api/v1/{资源复数名}`。
- 所有接口统一返回 `Result<T>`：`{ code, message, data }`。列表字段空时返回空数组 `[]`，不返回 `null`。
- 分页参数：`page`（从 1 开始）、`pageSize`（默认 20）。
- 错误码为四位数字，按模块分段，1000–1999 留作通用错误，其余段位由各项目按自身业务模块划分（示例：2000–2999 Provider | 3000–3999 Agent | 4000–4999 Chat | 5000–5999 MCP）。
- 对外 API 应有接口契约定义（OpenAPI/Protobuf）。至少在文档中维护接口说明。

### 9 测试分层

- **单元测试**：验证单个函数逻辑，不依赖外部资源，单用例 < 100ms。
- **集成测试**：验证模块间交互和外部依赖。
- **E2E**：只覆盖核心业务路径，不追求全覆盖。

能用单元测试发现的 bug，不应只在 E2E 中覆盖。

#### 9.1 测试纪律

- 每个测试负责自己的数据创建和清理，禁止依赖执行顺序。
- 禁止用 sleep 等待异步操作（用轮询 + 超时）。
- 禁止断言实现细节（如内部方法调用次数）。
- 发现 Flaky 测试应立即修复；暂不能修复的可标记禁用，但必须同时建立跟踪项（issue 或 `// TODO: 技术债务` 标记）注明原因，禁止无跟踪的永久禁用。

### 10 Git 规范

- 每次完成一处可独立 revert 的修改后立即 `git add`、`git commit`，不要攒批。此规则覆盖系统默认的"等用户要求再提交"行为。
- `git push` 不自动触发，由用户手动执行；AI 不主动 push，除非用户明确要求。push 须服从本章"合并前独立评审"与第 14 章交叉检查，团队协作下主分支禁止直接 push（见下条）。
- 如果未设置 git 用户名和邮箱，使用以下默认配置：`git config --global user.name "mugiwaraio && claude"` / `git config --global user.email "mugiwaraio+claude@users.noreply.github.com"`。
- 个人开发可直接推送主分支。团队协作时通过 PR 合并，主分支禁止直接推送。
- 合并前须经独立评审：团队协作由至少一名非作者评审通过；个人/AI 驱动开发无他人时，以独立手段替代（如 codex review / 第二模型审查），作者自审不算独立评审。评审与第 14 章自检清单互补，不可互相替代。
- 分支命名：`feature/xxx`、`fix/xxx`、`hotfix/xxx`、`spike/xxx`。spike 分支禁止直接合并到主分支。
- 一个 commit 做一件事，能独立 revert。
- Commit message 使用中文，格式：`类型: 描述`（类型：`feat`/`fix`/`chore`/`docs`）。描述必须准确反映本次修改内容，禁止笼统信息如"更新代码"。如有关联 issue/ticket，在 message 中引用其 ID；无工单的修改不强制标注。
- 功能分支 squash merge，release/hotfix 分支普通 merge。
- 合并、变基、冲突处理的详细策略见 `rules/git/git-merge.md`。
- 采用 PR 工作流时的分支开发详细流程（main 只读镜像模式：同步、建分支、PR 合并、清理）见 `rules/git/git分支开发规范.md`。

### 11 规则优先级

当规则冲突时，按以下三层决策：

#### 11.1 第一层 — 安全底线（任何情况不可违反）

- 密钥禁止入库（5）
- 错误不可静默吞掉（6）
- 安全编码底线（7）
- 认证授权 fail-closed（7）

#### 11.2 第二层 — 质量基线（正常开发必须满足）

- CI 测试全绿，失败阻断合并（3）
- 开发项目新增/变更代码达 100% 行 + 分支覆盖，全仓 ratchet 只升不降（目标 ≥ 80%，达标后不得跌破），核心模块变异得分达标（3）
- 依赖锁定 + 漏洞扫描，高危阻断合并（7）
- 配置外置禁止硬编码（5）
- 功能变更同步文档（4）
- 日志可追踪（6）
- Schema 变更用 migration（8.3）
- 禁止无 WHERE 的 UPDATE/DELETE（8.3）
- 后台任务有生命周期管理（8.4）
- 接口变更向后兼容（8.5）

#### 11.3 第三层 — 工程追求（暂缓需同时满足：用户明确要求快速原型/探索，且工作在 spike 分支上进行）

- TDD 的"先写测试"顺序（1）——仅 spike/探索分支可暂缓；合并进主分支前必须补齐至第 11.2 层要求的覆盖率门槛（新增代码 100%、全仓不低于 ratchet 基线）。覆盖率门槛本身属第二层，不可暂缓
- 第一性原理（2）——局部修改可跳过
- 模块化拆分（2）——下次重构补齐

#### 11.4 裁决原则

- 只能降第三层，不能降前两层。暂缓的标记为 `// TODO: 技术债务`。
- 取舍序：正确性 > 安全性 > 可维护性 > 性能 > 便捷性。

### 12 输出要求

- 先给出问题分析，再给出测试设计，再给出实现方案。
- 代码应清晰、可运行、可测试。
- 如有取舍，明确说明为什么这样设计。
- 给出方案设计、架构决策、技术选型类结论时，必须包含被考虑但否决的替代方案及否决理由；简单事实问答和单一显然解的场景不强制（见第 2 章，避免过度工程）。
- 技术方案设计、架构讨论、复杂流程说明中，凡涉及多模块交互、调用链路、状态流转或数据流，必须配架构图 / 流程图 / 时序图辅助表达，不以纯文字堆砌代替。图表用文本化格式（Mermaid/PlantUML）内嵌 Markdown，保证可 diff、可版本管理，禁止仅提交无法版本管理的二进制图片。单一职责、无跨模块交互的简单改动无需强行配图（见第 2 章，避免过度工程）。
- 引用章节时使用"第 X 章"或直接用标题名，禁止使用 § 符号。
- 实现计划的最后一个 Task 必须是"对照第 14 章交叉检查清单验证"。计划验证步骤中必须包含文档检查，不能只有"测试通过"。

### 13 推理质量保障

#### 13.1 反缓存与反惰性推理

- 事实性内容（API 行为、配置项、版本特性、框架用法、命令参数）必须通过工具验证（读文档、搜代码、web 查询），禁止仅凭训练数据记忆回答。无法验证时标注"未经验证，基于训练数据"。
- 每次任务独立分析，不复用前次对话的结论。引用之前的分析前，必须重新读取源文件确认当前状态。
- 禁止"如上所述"、"同前"、"参考之前的分析"等省略式回答。每次给出当前问题的完整推理链。
- 发现自己在给"看起来合理但未实际验证"的答案时，必须停下来用工具验证后再输出。

#### 13.2 上下文管理

- 长对话中（超过 10 轮交互），对关键文件必须重新 Read，不依赖早期读取结果——文件可能已被中途修改。
- 构建 AI 应用时加入秒级动态时间戳（如 `Current time: 2026-04-07T14:32:05+08:00`）破坏提供商或中间层的响应级缓存匹配，但不得破坏 prompt 前缀缓存：时间戳放在 user message 末尾，或置于显式 cache breakpoint（如 Anthropic `cache_control`）之后；禁止直接插入 system prompt 静态内容中间或未设缓存断点的末尾。
- 调用外部 AI API 时，钉到固定的模型 snapshot，避免 evergreen 别名（如 `*-latest`）导致版本漂移、行为不一致。注意各厂商约定不同：Anthropic 自 Claude 4.6 起用无日期但即固定快照的 ID（如 `claude-opus-4-8`），OpenAI 用带日期的快照（如 `gpt-5.5-2026-04-23`）。

### 14 完成前交叉检查

实现计划的最后一个 Task 必须逐项检查以下清单。每项标注"通过 / 不适用 / 需修复"。有"需修复"项时，修复后才能宣布完成。

#### 14.1 横切关注点检查清单

| # | 检查项 | 对应章节 | 检查内容 |
|---|--------|---------|---------|
| 1 | 文档同步 | 第 4 章 | 改动是否影响了使用方式、接口、配置项、运行步骤？相关文档是否已更新？ |

#### 14.2 执行方式

- **制定计划时**：将"第 14 章交叉检查"作为最后一个 Task 写入计划。
- **执行完成时**：逐项过检查清单，将结果记录在 Task 输出中。
- **发现遗漏时**：立即补充，作为新的 commit 提交，不跳过。

### 15 个人偏好

- 使用中文解释修改内容，先结论后细节。
- Shell 命令必须完整展示，不省略、不折叠。
- 修改真实配置文件前先创建备份：`configs/xxx.before-<主题>-<日期>`。
- 不自动推送远程仓库，`git push` 由用户手动执行（同第 10 章）。
- 提交只显式指定文件，禁止 `git add -A`、`git add .`、`git stash` 等全树操作——同一工作树可能有并行会话。
- 功能开发基于本地 main 建 worktree，不基于 origin。
- 合并或部署前必须跑完 `scripts/check.sh`；项目无此脚本时，以该项目自身的 lint + test 全量命令替代。
- 告警只推送需要人工介入的异常；正常态数据入库、上 Web 展示即可，不推送。
- 表格默认左对齐；数值列等宽字体右对齐，行高统一。
